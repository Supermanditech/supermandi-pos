# CAT-AUTO-001 — Automatic Category Assignment for Store Products

**Tag:** `cat-auto-001-2026-02-08`
**Branch:** `wip/cat-auto-001`
**Base:** `main` (SHA `60f9c79`)
**Date:** 2026-02-08

## Problem

Store products created via the **purchase/BUY flow** had no category (`taxonomy_id = NULL`) because the purchase service only wrote to `public.store_products` (which has no `taxonomy_id` column) and never bridged to `catalog.store_products` (which the categories API reads from).

This meant purchase-only products were invisible in category browsing on both POS and retailer dashboard.

## Root Cause

The backend has two parallel schemas:
- `catalog.*` — original catalog with taxonomy support (used by categories API)
- `public.*` — newer inventory/ledger system (used by purchase flow)

The purchase flow (`purchaseService.ts → applyStorePurchaseUpdates()`) only wrote to `public.store_products`, never bridging to `catalog.store_products`.

## Fix

### 1. Migration: Bridge + Backfill (114)
- Bridges `public.products` → `catalog.products` for purchase-only products
- Bridges `public.store_products` → `catalog.store_products` with auto-assigned `taxonomy_id`
- Re-backfills NULL taxonomy on existing `catalog.store_products` rows

### 2. Write-path: Auto-assign during purchase
- Modified `applyStorePurchaseUpdates()` to bridge every purchased product to catalog schema
- Calls `catalog.assign_taxonomy_by_name()` for each product (200+ keyword mappings, "Baaki" fallback)
- Preserves existing `taxonomy_id` on conflict (retailer overrides not clobbered)

### 3. API: `__uncategorized__` filter
- Categories products endpoint now handles `__uncategorized__` sentinel from POS PM-014
- Maps to `WHERE taxonomy_id IS NULL` instead of trying to match a UUID
