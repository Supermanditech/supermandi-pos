# SEC-001 — State-Based Feature Gating

**Category:** ACCESS CONTROL (MANDATORY)

**Scope:** Backend (ALL APIs)

---

## Implement

- Every sensitive endpoint checks:
  - store/supplier status
- POS/Web cannot bypass backend gating

---

## Acceptance

- [ ] Changing frontend alone cannot unlock features

### Current flow summary:

**Existing Middleware:**
- `backend/src/middleware/auth.ts` — JWT verification
- `backend/src/middleware/rateLimit.ts` — Rate limiting
- No status-based gating middleware

**Current Security:**
- Authentication required (JWT)
- Authorization by role (RBAC)
- No status-based access control

**Endpoints without status checks:**
- POS: `/api/v1/pos/*` — All accessible once authenticated
- Retailer: `/api/v1/retailer-admin/*` — All accessible once authenticated
- Supplier: `/api/v1/supplier/*` — All accessible once authenticated

### Gaps vs plan:

- [ ] **No status middleware**: Status not checked on any endpoint
- [ ] **Frontend only gating**: Current gating is UI-only (can bypass)
- [ ] **Inconsistent checks**: Ad-hoc status checks in some routes
- [ ] **No central enforcement**: Each route must implement own check

### Retailer Dashboard already covers part of this ticket?

**NO** — This is backend-only security. Retailer Dashboard UI gating is not sufficient.

## B) Implementation Subtickets (UI→API→DB)

### B.1) UI Subtickets

#### B.1.1) No UI changes needed
- This ticket is backend-only
- Frontend already has UI gating (defense in depth)
- Backend enforcement is the primary security layer

### B.2) API Subtickets

#### B.2.1) Store Status Middleware
- [ ] **SEC-001-API-STORE-MW**: Create store status middleware
  - File: `backend/src/middleware/storeStatusGate.ts` (NEW)
  - Extracts store_id from JWT or request
  - Queries store status from DB (with caching)
  - If status ≠ ACTIVE: Returns 403 with status info
  - Can be configured per-route for which statuses are allowed

```typescript
// Example usage
router.post('/sales', storeStatusGate('ACTIVE'), salesController.create);
router.get('/products', storeStatusGate(['ACTIVE', 'PAYMENTS_SUBMITTED']), productController.list);
```

#### B.2.2) Supplier Status Middleware
- [ ] **SEC-001-API-SUPPLIER-MW**: Create supplier status middleware
  - File: `backend/src/middleware/supplierStatusGate.ts` (NEW)
  - Same pattern as store middleware
  - Checks verification_status
  - Returns 403 if not ACTIVE

#### B.2.3) Apply to POS Routes
- [ ] **SEC-001-API-POS**: Apply middleware to POS endpoints
  - File: `backend/src/routes/v1/pos/index.ts` (MODIFY)
  - BLOCKED (require ACTIVE):
    - `POST /sales`
    - `POST /payments`
    - `GET /qr`
    - `POST /invoices`
  - ALLOWED (any authenticated):
    - `GET /products`
    - `POST /products`
    - `PUT /products/:id`
    - `GET /store`
    - `GET /store/status`

#### B.2.4) Apply to Retailer Routes
- [ ] **SEC-001-API-RETAILER**: Apply middleware to retailer endpoints
  - File: `backend/src/routes/v1/retailer-admin/index.ts` (MODIFY)
  - Most routes require ACTIVE
  - Auth routes exempt
  - Status check routes exempt

#### B.2.5) Apply to Supplier Routes
- [ ] **SEC-001-API-SUPPLIER**: Apply middleware to supplier endpoints
  - File: `backend/src/routes/v1/supplier/index.ts` (MODIFY)
  - All routes except auth require ACTIVE (verified)
  - Auth routes exempt
  - KYC submission routes allowed for KYC_SUBMITTED

#### B.2.6) Error Response Standard
- [ ] **SEC-001-API-ERROR**: Standardize 403 response
  - File: `backend/src/middleware/storeStatusGate.ts`
  - Response format:
    ```json
    {
      "error": "STATUS_NOT_ALLOWED",
      "message": "Your store is not active. Current status: PAYMENTS_SUBMITTED",
      "status": "PAYMENTS_SUBMITTED",
      "required_status": "ACTIVE"
    }
    ```

### B.3) DB/Migration Subtickets

#### B.3.1) No new migrations needed
- Status fields already exist
- No new columns required

### B.4) Caching Consideration
- [ ] **SEC-001-CACHE**: Status caching
  - Cache store/supplier status in Redis
  - TTL: 60 seconds
  - Invalidate on status change
  - Prevents DB query on every request
